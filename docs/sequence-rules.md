# 序列规则（已确认）

本文件是录制、识别、检定规则的唯一出处，代码和测试按编号引用（例如 `// R23`）。只收用户确认过的规则；没确认的放在文末“待确认”，不得当作规则实现。
来源：docs/score-retry-check.md（设计与实测记录）、docs/action-axis-knowledge-base.md、提交记录 5d310ed–e0925e5、和用户的商定（2026-10-27 至 10-29）。
新规则：用户确认后先追加到这里（带一行例子），再写代码。

## A. 环境与素材

- **R1** 游戏是 Windows 原生客户端，不在 Edge 或任何浏览器里运行；抓游戏画面不走浏览器/WebView 抓取。
  例：实战检定进程直接截取游戏窗口，不启动 WebView2。
- **R2** 只有 B 站视频录制用启动器自带的浏览器（WebView2，独立配置目录），不读取、不复用 Edge 的登录信息。
  例：录制器配置在 `%LOCALAPPDATA%\StarRailAutoBattle\WebView2Recorder`。
- **R3** B 站录制必须登录才能拿到 1080P（不登录只有 360P）；用户在启动器里自己登录，程序不输入账号密码。
  例：`recording_info.txt` 写着“登录状态：已登录 … 视频清晰度：1920×1080”。
- **R4** 不从外部直接调 B 站接口或用命令行下载（412 风控、下载被截断）；在录制器自己的页面里取视频流或截取播放画面；遇到 DRM 就停，不解密。
  例：请求 01:20–01:26 → 页面内取到 01:15–01:30 片段，1920×1080，7.6 MB。
- **R5** 录制或裁剪改动后检查输出分辨率，1080P 必须是 1920×1080，否则不算成功。
  例：输出 676×61（裁剪 bug）→ 失败，不能报告“录好了”。
- **R6** 盲测视频 BV18nVd6VEiB 永远不看画面，只在用户指定的片段上跑工具，再等用户答案。学习和标注只用三个开放视频：BV1EM8Q69EqZ（铁墓）、BV1vAgy6LE9G（绘世）、BV1pCaX6iEsU（亚婆离）。
  例：`scripts/check-samples.ps1` 遇到含 BV18nVd6VEiB 的样本直接跳过。
- **R7** 素材只在本地 `axis-data/` 沙箱里用，不转载、不上传；链接里的分享参数（vd_source）不写进提交的文件。
  例：`recording_info.txt` 记“链接：…/BV1EM8Q69EqZ/（已去掉分享参数）”。

## B. 序列里记什么

- **R8** 一份序列对应一整场战斗：从战斗开始到结算画面。混沌回忆上下半场之间算一次换波。
  例：上半场结束 → `== 换波 ==` → 下半场从 `1` 开始。
- **R9** 只记我方单位（角色、忆灵、召唤物、特殊单位）；敌方行动和 boss 机制条目（红色菱形）都不记。
  例：铁墓 0:50 附近的敌方回合、2:52 的 boss 机制条目不出现在序列里。
- **R10** 主轴行动 `n` 是本段第 n 次主轴行动；被控制跳过的回合也算。
  例：昔涟被冻结跳过的回合仍写 `5 昔涟`。
- **R11** 额外行动 `n-i` 挂在被它打断的主轴行动 n 下面；连续释放的多个终结技依次是 n-1、n-2…；本段第一次主轴行动之前的写 `0-1`、`0-2`。
  例：长夜月的主轴行动 7 中，昔涟终结技进当前格还没放，又按了忆灵昔涟的终结技 → `7-1 昔涟 终结技`、`7-2 忆灵昔涟 终结技`。
- **R12** 额外回合不能算作主轴行动。
  例：小伊卡在风堇回合中途的额外回合写 `12-1 小伊卡`，不是 `13 小伊卡`。
- **R13** 换波、转阶段写成特殊行动 `== 换波 ==`、`== 转阶段 ==`，之后序号从 1 重新开始。
  例：`9 迷迷` → `== 转阶段 ==` → `1 昔涟`。
- **R14** 额外行动不全是终结技：看到终结技启动的才写“终结技”，只有四角星标记的额外行动不写招式。
  例：`3-1 长夜月 终结技`（有启动）；`9-3 小伊卡`（只有四角星）。
- **R15** 阿哈时刻写成一行主轴行动，它触发的欢愉技写在括号里，不拆成额外行动。
  例：`5 阿哈时刻（含阿哈时刻附加行动：爻光、真珠）`。

## C. 文本格式

- **R16** 一行一步：`序号 单位 [招式] [目标] [@ 条件]`，空格分隔，`#` 后是注释；招式是普攻、战技、终结技。
  例：`2 昔涟 战技 敌2  @ 轮次=1 行动值=120~160  # 第1波`。
- **R17** 目标不写箭头。旧写法 `→敌2`、`->敌2` 仍能读，保存时去掉箭头。不发明新语法。
  例：写 `2 昔涟 战技 敌2`，不写 `2 昔涟 战技 →敌2`。
- **R18** 目标有两种写法，可以混用：从左数 `敌1`、`敌2`…（换波或有敌人倒下后按当时位置重数）；以 boss 为基准 `敌(0)`、`敌(-1)`、`敌(+1)`…（没有 boss 或有多个 boss 时只用从左数）。我方目标写 `我1`、`我2`…（画面表现待学）。
  例：boss 左边那只小怪写 `敌(-1)`，场上从左数第一只写 `敌1`。
- **R19** 不填目标时，操作上默认打 boss（`敌(0)`），没有 boss 时用游戏默认目标；从视频识别出的序列暂不填目标。
  例：`3 记忆主 普攻` → 自动操作打 boss。
- **R20** 条件 `@ 轮次=… 行动值=…` 可只写一项，值可写区间；换波、转阶段默认不读，写了 `@` 才读。
  例：`== 转阶段 ==  @ 行动值=50~100`。
- **R21** 单位写名称或 U 编号；知识库里没有的名称、一个名称对应多个单位、敌方单位都报错。识别不出写“未知”并注明，由人工改。
  例：`13-9 未知 终结技  # 单位看不清，请改成名称或 U 编号` → 格式检查报错，直到改成 `13-9 风堇 终结技`。
- **R22** 全角符号和全角数字都认。
  例：`２ 昔涟 敌（－１） ＠ 行动值＝１２０～１６０` 和半角写法等价。

## D. 画面识别

- **R23** 战斗开始 = 秘技后先黑屏，然后画面中间出现一条白线（连续两帧），不是某个界面元素出现。没看到时从第一个行动或第一条横幅算起，并注明“未检测到战斗开始”。
  例：三个开放视频都在 7–8 秒看到白线；铁墓草稿写“# 战斗开始（视频 0:08.0）”。
- **R24** 换波 = 画面上方出现“战斗开始 x/n”横幅；战斗开始后的第一条是第 1 波，之后每出现一条算一次换波，4 秒内重复出现不算。
  例：绘世 3:07.9 的横幅 → `== 换波 ==`。
- **R25** 转阶段 = boss 血条到 0% 且血条上方亮着的红点少一个，并保持 2 秒（特效遮住约 0.5 秒不算）；打掉这一阶段的那次行动留在旧阶段。
  例：绘世 7:02.2 红点从 2 个变 1 个 → `== 转阶段 ==`。
- **R26** 战斗结束 = “结束战斗”或“挑战成功”横幅连续两帧。失败画面还没有样本。
  例：铁墓 9:50–9:57：“结束战斗” → 黑屏 → “挑战成功”。
- **R27** 回合起点 = 当前格白闪（格内 80% 以上近白），或当前格的标记、单位改变并保持 0.2 秒；白闪后 0.4 秒内的改变算同一回合。同一单位连续两个回合只能靠白闪区分。
  例：终结技光束扫过只有约 47% 近白，不算白闪。
- **R28** 回合类型看当前格左侧标记：青色圆点 = 我方主轴；青色四角星（用户说的“小叉号”）= 额外行动；红色圆点 = 敌方；红色菱形 = boss 机制条目。
  例：当前格是青色四角星 → 写成 `n-i`。
- **R29** 终结技由按键操作：队伍栏头像亮起是启动，按下释放键才释放。队伍栏每个头像右边的终结技按钮亮着 = 就绪，按下后熄灭。启动信号不是插入卡（见 R45）。
  例：2 号位按钮就绪 1 秒后熄灭 → 2 号位在这一刻释放了终结技。
- **R30** 队伍栏位置 → 单位只用用户给的队伍（`--team` 或启动器“队伍”栏），不从画面学、不猜；没给队伍时只标“队伍第几位”。
  例：`axis sequence … --team 昔涟,长夜月,风堇,记忆主`；自己学过一次，把长夜月的终结技标成了忆灵昔涟。
- **R31** 招式不能靠战技点判断（有的战技不耗点，有的普攻不回点）；看选招状态里被放大的按钮，取行动开始执行前最后一次清楚的读数。
  例：铁墓 0:17.7 先选普攻 1.5 秒，最后几帧换成战技 → 写 `战技`。
- **R32** 轮次和剩余行动值在行动进行中读（行动中不变），同一步至少两帧一致；任何一位数字拿不准就整条作废，按待定处理。
  例：读到“⌛2 | 238”两帧一致 → `轮次=2 行动值=238`。

## E. 检定

- **R33** 和预期序列相比，多了、少了、顺序反了，或类型（主轴、额外、特殊）不对，都判失败；结算时序列没走完，或走完后又出现行动，也判失败。
  例：预期 `3-1 长夜月 终结技`，实战没有这一步 → 失败。
- **R34** 招式和目标不参与判定。
  例：预期 `2 昔涟 战技`，实战是普攻 → 不因此判失败。
- **R35** 看不清、拿不准判待定，不判失败；每步在出现后 1 秒内给出判定。（“宁可不重开”已被 R76 改掉：每局待定超过容许次数就重开。）
  例：单位认不出 → 输出待定，继续看下一步。
- **R36** 判失败或重开后继续看画面，下次检测到战斗开始（R23）就从第 1 步重新比对。（待定没超过 R76 的容许次数时，这一局继续比对。）
  例：重开后黑屏白线出现 → 比对回到 `1`。
- **R37** 检定是单独的进程：自己截取游戏窗口，每个事件输出一行 JSON；只读屏幕，不读内存、不注入游戏进程。重开由队友的程序负责，模拟按键由操控端 `srctl` 负责（R61）。
  例：每检测到一步就输出一行 JSON 供队友程序读取（字段格式还没定）。

## F. 单位与知识库

- **R38** 每个不同的行动轴头像一个全局编号 `U0001…`：同一头像同一编号，不同头像不同编号；颜色或状态变体（如发红）是同一单位。名称是用户的备注，用户确认后才写入。
  例：发红的昔涟头像仍是昔涟的 U 编号，不新开编号。
- **R39** 盲测中的新头像用临时编号 `新01…`，知识库冻结；用户核对后才通过 `axis kb promote` 转正。拿不准标“疑似”，不自动合并。
  例：用户答“新01 = U0012” → 合并进 U0012。
- **R40** 屏幕文字（如“这里”）和轴底的剩余行动值条不是单位。
  例：识别结果里出现“这里”格 → 丢弃，不进知识库也不进序列。

## G. 测试与流程

- **R41** 每次改检测器后，在主目录跑 `pwsh scripts/check-samples.ps1`，报告逐条差异和按类型的精确率、召回率；`expected.txt` 由用户确认，不为了通过而修改。
  例：改了白闪阈值 → 跑脚本 → 报告“铁墓：不一致 3 处”。
- **R42** 和用户答案比对时先对齐，再把每处差异交给用户裁定（工具错 / 答案笔误 / 不确定）；只有“工具错”才变成修正和知识库数据，工具的原始输出不改。
  例：工具漏了一步导致后面序号整体错位 → 先对齐，只报这一处。
- **R43** 测试遗留文件：自己的临时输出（草稿区、临时程序）立刻删；录像和盲测结果先列清单（带大小），用户同意再删。
  例：3 分钟录像约 1.2 GB → 列出来问用户。
- **R44** 规则不清楚时先问；用户回答后先写进本文件（带例子），再写代码和测试。
  例：用户确认“星标额外行动不写招式” → 先加 R14，再改 EventAnalyzer。

## H. 后续确认（按确认顺序追加）

- **R45** 插入卡（当前格右边的拱顶小卡）不可靠：它和终结技启动不是同一时刻，不能用来判断启动，也不能用来给终结技计数。终结技只看队伍栏（R29）。（用户 2026-10-29，回答 Q1）
  例：出现一张新插入卡，但队伍栏没有任何一位熄灭 → 不记终结技。
- **R46** 昔涟那一位的水晶心形图标也有可读的“亮/灭”：亮 = 就绪，按下后熄灭，和其他位置的终结技按钮一样按 R29 读，不再靠插入卡或四角星认她的终结技。（用户 2026-10-29，回答 Q5）亮和灭具体长什么样待学（Q5a）。
  例：昔涟在 1 号位，心形图标由亮转灭并保持 1 秒 → `n-i 昔涟 终结技`。
- **R47** 识别要跟得上快的操作：每一步在出现后 0.5 秒内认定（比 R35 的 1 秒更紧）。（用户 2026-10-29：“识别时间看看能不能提速到 0.5 秒，考虑到视频操作可能会比较快”）
  例：Release 版每帧约 27 ms，按每秒 15 帧截图，回合在开始后约 0.25 秒（3 帧一致）认定。
- **R48** 启动器手动编辑序列时：行首序号（`3`、`3-1`）打完后接着打别的字，自动在中间补一个空格；已经有空格的地方再打空格不添加；格式里用不到的符号（如 `→`、`|`、`;`）打了也不添加。`#` 后的注释不受限制；粘贴的内容不改动，照常由格式检查报错。（用户 2026-10-29）
  例：依次打 `3`、`昔`、`涟`、空格、空格、`|`、`战技` → 编辑框里是 `3 昔涟 战技`。

- **R49** 样本视频用录制器下载的视频（`axis record … --method download`，页面内下载，R4），铁墓、绘世、亚婆离各 0:00–3:00；下载后检查是 1920×1080（R5）才能用，样本的 `sample.json` 指向下载的文件。（用户 2026-10-29）
  例：`samples/铁墓…/sample.json` 的 `video` 从旧录像 `recording.avi` 改成下载的 `recording.mp4`。
- **R50** 样本的正确答案这样来：工具先用下载的视频生成草稿 `samples/*/draft.txt`，用户核对改正后另存为 `expected.txt`；没有 `expected.txt` 的样本不拿来调识别器。（用户 2026-10-29）
  例：工具写 `draft.txt` → 用户改好存为 `expected.txt` → `check-samples.ps1` 开始比对这个样本。

- **R51** 只看到队伍栏按钮熄灭、没进当前格的终结技，挂在熄灭那一刻正在进行的主轴行动下（R11），连按几个就依次 n-1、n-2…。（用户 2026-10-29，回答 Q6）
  例：记忆主的主轴行动 3 进行中，2 号位按钮熄灭 → `3-1 长夜月 终结技`（队伍里 2 号位是长夜月）。
- **R52** 队伍栏按钮熄灭后，当前格出现同一单位的四角星回合（暂定 6 秒内），是这个终结技进当前格等待释放，算同一个，不重复记。（用户 2026-10-29）
  例：0:57.1 2 号位熄灭、1:00.1 当前格四角星长夜月 → 只记一行 `9-1 长夜月 终结技`。

- **R53** 为了让队友测试，知识库识别必需的部分提交进私有仓库（只有队友能看）：`axis-data/kb` 的 json 索引、`samples/` 头像样本、`cues/` 线索样本。视频整帧截图（`kb/screenshots/`）、录像和下载的视频、测试运行结果、盲测相关的录像都不提交；队友用启动器自己下载样本视频（R49）。这是对 R7 的放宽，只限这些文件。（用户 2026-10-29）
  例：`git add axis-data/kb/units.json axis-data/kb/samples/…` 可以；`axis-data/recordings/…/recording.mp4` 不提交。

- **R54** 启动器手动编辑序列时，序号随插入、删除自动调整（用户 2026-10-29）：
  - 新开一行写行动（序号打完、后面有了空格），本段后面已有同号的行 → 后面的序号 +1；整行删掉一个行动，本段后面紧接着是下一个号 → 后面的序号 −1。
  - 主轴 `n` 变时，后面挂在它下面的 `n-i` 跟着变（R11）；插入或删除额外行动 `n-i` 只改同一主轴下后面的额外行动。
  - 只改到本段结束，换波、转阶段之后不动（R13）；只改行首序号，其余内容不动。
  - 改旧行的序号、撤销和重做不触发；删掉主轴行动时，它下面的额外行动不改，由格式检查报错。
  例：`2 昔涟`、`3 长夜月`、`3-1 风堇 终结技`、`4 记忆主`，在 `2 昔涟` 后新开一行打 `3 风堇` → 后面变成 `4 长夜月`、`4-1 风堇 终结技`、`5 记忆主`；再整行删掉 `3 风堇` → 恢复原样。

- **R55** 终结技另做一套识别：只看终结技的全屏立绘和右下角的终结技释放按钮，和队伍栏按钮（R29）那套并行，`check-samples.ps1` 两套各出统计，比较后再定用哪套。（用户 2026-10-29）

## I. 操控端

- **R61** 操控端是单独的命令行程序 `srctl`（`src/GameControl`），不放在启动器里；它只给游戏窗口发按键，不读内存、不注入游戏进程。这修改了 R37 的“模拟操作由队友的程序负责”：按键改由 `srctl` 发，检定进程仍只读屏幕。（用户 2026-11-02）
  例：`srctl send skill` → 游戏收到一次 E。
- **R62** 指令接口：`srctl serve` 从标准输入每行读一个 JSON 指令，每条指令在标准输出回一行 JSON 回执；`srctl send <操作>` 发一次就退出。操作只有：`basic` 普攻、`skill` 战技、`ult` 终结技（带 `slot` 1–4，队伍几号位）、`confirm` 确认释放、`left`/`right` 换目标、`menu` 菜单。读不懂的指令回 `ok:false` 和原因，不猜。（用户 2026-11-02）
  例：输入 `{"op":"ult","slot":2}` → 回 `{"ok":true,"op":"ult","slot":2,"key":"2","ms":0.1}`；输入 `{"op":"ult"}` → 回 `{"ok":false,"error":"ult 需要 slot 1–4"}`。
- **R63** 后台发键：用 PostMessage 把按下、抬起消息直接发给游戏窗口，游戏不用在前台，不切前台、不用 SendInput。游戏不认就如实报告，不改用注入或驱动。游戏以管理员身份运行时 `srctl` 也要以管理员身份运行，否则 Windows 拒绝，回执报“拒绝访问”。（用户 2026-11-02）
  例：游戏在后台，`srctl send basic` 回 `ok:true`，前台窗口不变；游戏要真正处理还需开假激活（R66）。
- **R64** 键位默认 `basic`=Q、`skill`=E、`ult` 1–4 号位=1–4、`confirm`=空格、`left`=A、`right`=D、`menu`=Esc，可用 `srctl keys set <操作> <键>` 改，存在 `%LOCALAPPDATA%\StarRailAutoBattle\control-keys.json`。（用户 2026-11-02）
  例：`srctl keys set confirm E` → 之后 `confirm` 发 E。
- **R65** 反应要快：`serve` 常驻，游戏窗口找到后缓存（窗口关了再重找）；每个键按下后按住 `hold` 毫秒再抬起（默认 30，可改），回执里的 `ms` 是从读到指令到发出按下的耗时。（用户 2026-11-02 “反应要灵敏”）
  例：连续发 `{"op":"ult","slot":1}`、`{"op":"confirm"}` → 两条回执的 `ms` 都在 1 以内。
- **R66** 实测（2026-11-02）：只用 PostMessage 发键，游戏在后台不处理（普攻、终结技、Esc 都要切到前台才生效）。为此加一个开关“假激活”，默认关：开着时每次按下前先给游戏窗口发“已激活”消息（WM_ACTIVATEAPP、WM_ACTIVATE、WM_SETFOCUS），游戏仍留在后台，不切前台、不注入（R63 其余不变）。用 `srctl keys activate on|off` 开关，存在键位文件里；回执里带 `"activate":true`。这是在骗游戏。（用户 2026-11-02 选“先试假激活”）实测：开着假激活、`srctl` 以管理员身份运行，游戏在后台时普攻、终结技都立刻生效；假激活后在前台别的窗口按 Q、E、1、空格、Esc，后台游戏没反应，所以按完不发“未激活”（用户 2026-11-02）。
  例：`srctl keys activate on` → `srctl send basic` 时游戏依次收到 WM_ACTIVATEAPP、WM_ACTIVATE、WM_SETFOCUS、Q 按下、Q 抬起。
- **R67** 终结技键按下后，游戏要过一会儿才接得住确认：实测间隔 600 ms 能放出（1 号位），300 ms 放不出（2 号位），确认键是空格（用户 2026-11-02）。所以 `confirm` 离上一次 `ult` 按下不到 `gap` 毫秒时，srctl 自己等够再按；中间夹着换目标也算，按过 `confirm` 就清掉，给战技的确认不等。`gap` 默认 600，用 `srctl keys gap <毫秒>` 改（0–5000），存在键位文件里（`gap` 已并入 R71 的 `splash`）。等过的话回执带 `"wait":毫秒数`，`ms` 不含等待（R65）。（用户 2026-11-02 选“srctl 自动等”）
  例：连着发 `{"op":"ult","slot":1}`、`{"op":"confirm"}` → 第二条回执 `{"ok":true,"op":"confirm","key":"Space","wait":570,"ms":0.4}`。
- **R68** 终结技动画期间游戏不收任何按键（实测：连放两个终结技，第二个丢了，用户 2026-11-02）。所以给终结技按的 `confirm`（前面有没确认的 `ult`）按下后，下一个按键至少等 `anim` 毫秒；`anim` 默认 3000（R69 改，原 2500），用 `srctl keys anim <毫秒>` 改（0–20000），存在键位文件里。调用方可以在指令里写 `"after":毫秒数`（0 或正整数）：从上一个按键按下起等这么久再按，上一个是终结技的确认时就是从它释放那一刻起（同 R60）；写了 `after` 就只按它等，不再套 `anim` 和 R67 的 `gap`。等过的话回执带 `"wait"`（同 R67）。（用户 2026-11-02）
  例：`{"op":"ult","slot":1}`、`{"op":"confirm"}`、`{"op":"ult","slot":2}` → 第三条等到第一个终结技释放 3 秒后才按；写成 `{"op":"ult","slot":2,"after":1200}` → 释放 1.2 秒后就按。
- **R69** 实测：1 号位终结技带附带行动时，等 2.5 秒后 2 号位的终结技键按进去了，但确认没接住（用户 2026-11-02）。所以（用户 2026-11-02）：
  - `anim` 默认改为 3000，每个号位可以单独设：`srctl keys anim <号位> <毫秒>`（号位对应用户给的队伍，R30；换队伍要重配），`srctl keys anim <毫秒>` 只改默认。
  - 终结技可以连按、再一个个确认：`ult` 紧跟在 `ult` 后面（中间没有 `confirm`）时，离上一个终结技键按下至少隔 `ultgap` 毫秒，默认 300，用 `srctl keys ultgap <毫秒>` 改（0–5000）；其他键不受影响（`ultgap` 已并入 R71 的 `splash`）。
  - 每个 `ult` 排一个，每个 `confirm` 释放一个，排着的都释放完才清掉 R67 的记录。一批只排了一个时，确认后等这个号位的 `anim`；一批排了几个时，不知道哪次确认放的是谁（Q8），每次确认后等这批里最长的 `anim`，不猜顺序。
  例：`keys anim 1 4500` 后发 `ult 1`、`ult 2`、`confirm`、`confirm` → 2 号位的键在 1 号位键 300 ms 后按，第一个确认在 2 号位键 600 ms 后按，第二个确认在第一个确认 4.5 秒后按。
- **R70** srctl 现在不做图像识别，不截游戏画面；“确认按钮出现了没有”这类画面判断以后再对接（Q8）。在那之前只按 R67–R69 的时间等，调用方可以用 `after` 自己定时。（用户 2026-11-02）
  例：连按两个终结技后逐个确认 → srctl 不看画面，第二个确认按 R69 等这批里最长的 `anim`。
- **R71** 按下终结技键后先放约 1–2 秒立绘，立绘放完才能按下一个终结技键，确认也要等立绘放完；确认还要等前一个终结技的技能动画放完（R68、R69 不变）。（用户 2026-11-02 观察）所以 R67 的 `gap` 和 R69 的 `ultgap` 合并成一个 `splash`：`ult` 或 `confirm` 离上一个终结技键按下（还有没确认的终结技时）不到 `splash` 毫秒就等够再按；其他键不等。`splash` 默认 800（实测 0.8 秒一般可行，原定 1500），用 `srctl keys splash <毫秒>` 改（0–5000）；`keys gap`、`keys ultgap` 去掉。（用户 2026-11-02）
  实测（用户 2026-11-02）：1 号位风堇的终结技后面还有忆灵技，`anim` 3000/4500 时下一个确认接不住；`keys anim 1 8000`、`splash` 800 时，“放一个确认一个”和“先连按再逐个确认”两种连放都成功。带忆灵技、附带行动的号位要单独设长的 `anim`。
  例：发 `ult 1`、`ult 2`、`confirm`、`confirm` → 2 号位的键在 1 号位键 0.8 秒后按，第一个确认在 2 号位键 0.8 秒后按，第二个确认等这批最长的 `anim`。
- **R72** `basic`、`skill` 默认按两次：按一下、抬起后等 `twice` 毫秒、再按一下（第一下选中，第二下放出），这样不用管当时选中的是普攻还是战技。`twice` 默认 300，用 `srctl keys twice <毫秒>` 改（0–2000），0 = 只按一次。回执带 `"presses":2`，`ms` 到第一下按下为止（R65）；`after` 的“上一个按键按下”算第二下（放出的那一刻，同 R60）。其他操作只按一次。（用户 2026-11-02）
